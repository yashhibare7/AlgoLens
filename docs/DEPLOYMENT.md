# Deploying AlgoLens for free

The whole app ships as **one Docker image**: the React bundle is baked into the Spring Boot jar
and served by it. One service, one URL, no CORS. That is the shape that fits a free tier, where
every extra service is another cold start to pay for.

**Recommended free stack — no credit card needed:**

| Piece | Where | Free tier |
|---|---|---|
| App (API + UI) | **Render** | 512 MB, sleeps after 15 min idle |
| Database | **Neon** | 0.5 GB Postgres, does not expire |
| AI explanations | *optional* | Works without a key using the built-in local explainer |

Total: **₹0/month**, about 20 minutes of setup.

---

## Before you start

You need a **GitHub account** and this project pushed to a repo. Everything else is browser
work.

```bash
cd f:\ProjectPro\AlgoLens
git init
git add .
git commit -m "AlgoLens"
git branch -M main
git remote add origin https://github.com/YOUR_USERNAME/algolens.git
git push -u origin main
```

`.gitignore` already excludes `.env`, `backend/data/`, `node_modules/` and `target/`, so no
secrets or build output go up.

> Docker is **not** installed on this machine, so the image could not be built and run here.
> The parts that Docker only packages — the SPA being served by Spring Boot, client-side routes
> falling back to `index.html`, the API staying JSON — were verified by running the packaged jar
> directly. The Dockerfile itself is unverified until you build it; if it fails, the build logs
> on Render will say where.

## Step 1 — Database (Neon, 3 minutes)

1. Go to <https://neon.tech> and sign in with GitHub.
2. **Create project** — name it `algolens`, pick the region closest to you.
3. On the dashboard, find **Connection string** and switch the format to **Java** (or copy the
   psql one and convert it — see below).

Neon gives you something like:

```
postgresql://alex:npg_AbC123@ep-cool-name-12345.ap-southeast-1.aws.neon.tech/neondb?sslmode=require
```

Split that into the three values Render will need:

| Variable | Value from the string above |
|---|---|
| `ALGOLENS_DB_URL` | `jdbc:postgresql://ep-cool-name-12345.ap-southeast-1.aws.neon.tech/neondb?sslmode=require` |
| `ALGOLENS_DB_USER` | `alex` |
| `ALGOLENS_DB_PASSWORD` | `npg_AbC123` |

**Two things people get wrong here.** The URL must start with `jdbc:postgresql://` — not
`postgresql://`. And the username and password must be *removed* from the URL and passed
separately, or the driver and the credentials will fight.

Keep `?sslmode=require`. Neon refuses plaintext connections.

## Step 2 — Deploy the app (Render, 10 minutes)

1. Go to <https://render.com> and sign in with GitHub.
2. **New → Blueprint**, pick your repo. Render finds [`render.yaml`](../render.yaml) and
   proposes one web service called `algolens`.
3. It will ask for the three values marked `sync: false`. Paste the Neon values from step 1.
4. **Apply**.

The first build takes **8–12 minutes** — it installs npm packages, builds the frontend,
downloads Maven dependencies and compiles the backend. Later deploys are faster because Docker
caches the dependency layers.

When it finishes you get `https://algolens-XXXX.onrender.com`. Open it: the visualizer loads,
and the problem library is already seeded because Flyway ran the migrations and `ProblemSeeder`
filled the tables on first boot.

`ALGOLENS_JWT_SECRET` is generated by Render (`generateValue: true`) and kept across deploys, so
there is nothing to invent and nothing to leak.

### Prefer clicking to blueprints?

**New → Web Service** → pick the repo → **Runtime: Docker** → **Plan: Free**, then add the
environment variables from `render.yaml` by hand. Same result.

## Step 3 — AI explanations (optional, 1 minute)

The AI panel already works without this: a built-in local explainer answers, free, and labels
itself so nobody mistakes it for a model.

For real explanations, add one more environment variable in Render:

```
ANTHROPIC_API_KEY = sk-ant-...
```

Get a key at <https://console.anthropic.com>. It is read **server-side only** — the browser
calls your own `/api/ai/explain`, so the key never reaches a client bundle.

This one is not free: it is billed per request by Anthropic. Credits are metered per user in the
app, and you can enforce them by setting `ALGOLENS_CREDITS_ENFORCED=true` so a user cannot run up
your bill.

## The catch with free hosting, stated plainly

**Render free services sleep after 15 minutes of inactivity.** The next request has to start the
container and the JVM, which takes **30–60 seconds**. A visitor clicking your portfolio link sees
a blank page for that long, then everything is fast.

The frontend already says so — a failed request on a deployed build reads *"It may be asleep —
free hosting spins down when idle, so the first request can take up to a minute."*

Things that genuinely help:

- **Say so on the page.** A line like "hosted free, first load may take a minute" turns a bug
  into a known quantity.
- **Do not use an uptime pinger to keep it awake.** Render's free tier has a monthly hours
  budget; pinging burns it and the service stops for the rest of the month. It also violates
  their terms.
- **Upgrade when it matters.** Render's paid tier is $7/month and never sleeps. If this is going
  on a CV, it is worth it the week before an interview.

Other free-tier realities:

| Limit | What it means here |
|---|---|
| 512 MB RAM | Fine. The Dockerfile sets `MaxRAMPercentage=70` and `UseSerialGC` for exactly this |
| Ephemeral disk | Nothing is stored on disk — the database is Neon. Do **not** use the `dev` H2 profile in production or all data vanishes on every restart |
| Shared CPU | Execution is capped at 5 s wall clock anyway |
| No rate limiting | Anonymous execution is open. If it gets abused, set `ALGOLENS_ALLOW_ANONYMOUS_EXECUTION=false` |

## Other free options

### Single service, like Render

| Platform | Notes |
|---|---|
| **Koyeb** | Free tier, Docker, and it does **not** sleep. Smaller instance, no card |
| **Fly.io** | Good, fast, `fly launch` reads the Dockerfile. Requires a card even on the free allowance |
| **Google Cloud Run** | Very generous (2M requests/month), scales to zero, cold start ~10 s — better than Render's. Requires a billing account |
| **Hugging Face Spaces** | Docker Space, 16 GB RAM, genuinely free. Odd fit for a web app, but it works |
| **Oracle Cloud Always Free** | A real always-on VM (ARM, 24 GB RAM). The most generous by far, and the most setup — you manage the box yourself |

### Split: UI and API separately

Only worth it if you want the UI on a CDN so *it* loads instantly while the API wakes up.

1. **Frontend → Vercel / Netlify / Cloudflare Pages.** Root directory `frontend`, build command
   `npm run build`, output `dist`. Add an environment variable:

   ```
   VITE_API_BASE_URL = https://algolens-XXXX.onrender.com
   ```

   It is read at build time, so you must redeploy after changing it.

2. **Backend → Render**, same as above, plus:

   ```
   ALGOLENS_CORS_ORIGINS = https://your-app.vercel.app
   ```

   Both halves are required. Miss the CORS variable and the browser blocks every call with an
   error that says nothing useful about the cause.

The single-service setup avoids all of this, which is why it is the recommendation.

## Every environment variable

| Variable | Required | Purpose |
|---|---|---|
| `SPRING_PROFILES_ACTIVE` | **yes** | Must be `postgres` in production. The default `dev` uses a local H2 file that a container throws away |
| `ALGOLENS_JWT_SECRET` | **yes** | HS256 key, min 32 bytes. The app refuses to start with anything shorter — deliberately, so a weak key cannot ship by accident |
| `ALGOLENS_DB_URL` | yes (postgres) | `jdbc:postgresql://host/db?sslmode=require` |
| `ALGOLENS_DB_USER` / `_PASSWORD` | yes (postgres) | Separate from the URL |
| `PORT` | auto | Injected by the platform; the Dockerfile passes it through |
| `ANTHROPIC_API_KEY` | no | Enables real AI explanations |
| `ALGOLENS_CORS_ORIGINS` | no | Only for split deployments |
| `ALGOLENS_CREDITS_ENFORCED` | no | `true` makes credits actually refuse requests |
| `ALGOLENS_ALLOW_ANONYMOUS_EXECUTION` | no | `false` requires an account before running code |

Generate a secret:

```bash
openssl rand -base64 48
```

```powershell
# Windows, no openssl
[Convert]::ToBase64String((1..48 | ForEach-Object { Get-Random -Max 256 }))
```

## Test the image locally first

If you install Docker, catch problems before they reach a build log:

```bash
docker build -t algolens .
docker run -p 8080:8080 -e ALGOLENS_JWT_SECRET=$(openssl rand -base64 48) algolens
```

Open <http://localhost:8080>. With no database variables it runs on the `dev` H2 profile, which
is fine for checking that the image works.

Without Docker, you can still verify the same thing the image does:

```powershell
cd frontend;  npm run build;  cd ..
New-Item -ItemType Directory -Force backend\src\main\resources\static | Out-Null
Copy-Item -Recurse -Force frontend\dist\* backend\src\main\resources\static
cd backend;  .\mvnw.cmd -DskipTests package
java -jar target\algolens-backend-0.1.0.jar
```

Then check <http://localhost:8080> serves the UI and <http://localhost:8080/api/meta> returns
JSON. Delete `backend/src/main/resources/static` afterwards — it is generated, and it is
git-ignored for that reason.

## When it goes wrong

**Build fails on `npm ci`** — `package-lock.json` is not committed. `git add -f frontend/package-lock.json`.

**"algolens.jwt.secret must be at least 32 bytes"** — working as designed. Set a longer
`ALGOLENS_JWT_SECRET`.

**App starts, every page is a white screen** — the frontend build did not land in the image.
Check the build log for the `npm run build` stage, and that `.dockerignore` is not excluding
something it needs.

**`FATAL: password authentication failed`** — credentials are still embedded in
`ALGOLENS_DB_URL`. Strip them out into `ALGOLENS_DB_USER` and `ALGOLENS_DB_PASSWORD`.

**`The server does not support SSL`** or connection hangs** — `?sslmode=require` is missing from
the JDBC URL. Neon requires it.

**First request after idle times out** — that is the cold start, not a failure. Wait and retry.

**`Flyway ... validate failed`** — the database has a partial schema from a failed first deploy.
On Neon, drop and recreate the database (it is empty anyway), then redeploy.

**Out of memory / container killed** — check that `SPRING_PROFILES_ACTIVE=postgres`. Running H2
in a 512 MB container alongside the JVM is what usually pushes it over.
